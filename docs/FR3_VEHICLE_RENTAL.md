# DRIVE — Vehicle Rental (PDF requirement 3 / detailed SRS FR-05)

This feature is being implemented requirement-by-requirement. It uses the existing TypeScript/Firebase rental API rather than trusting the mobile client to create booking records.

## Renter flow

1. Open **Vehicle rentals** from the Rider screen.
2. Filter approved car/bike/premium listings by category, area text and maximum hourly price.
3. Choose start and end dates/times.
4. Review the estimated total and confirm.
5. The backend validates the vehicle and owner approval, prevents self-rental, reserves all required hourly slots in a Firestore transaction, and returns the authoritative total.
6. View booking status/history. Cancel a confirmed booking before its start; cancellation releases the reservation locks transactionally.

## Vehicle-owner flow

1. Apply to become a vehicle owner and wait for admin approval.
2. Open the Owner tab and select **Add vehicle**.
3. Enter model, registration/plate number, type, seat count, hourly BDT rate and area.
4. The backend stores public listing data separately from private plate/registration information and marks the listing pending.
5. See the listing's pending/approved/rejected status and bookings for owned vehicles. Owners can cancel a future confirmed rental.

## Security and business rules

- Only approved, rental-enabled vehicles appear in the public query.
- Owner profile must be approved before listing a vehicle.
- The server calculates totals in integer paisa; clients cannot write vehicles or rental bookings directly.
- A renter cannot book their own vehicle.
- Reservation locks prevent overlapping bookings for the same vehicle, including concurrent requests.
- Backend policy currently permits a start within the next 90 days and a rental duration of up to 72 hours.
- Registration/plate data is stored in the private vehicle collection and is not included in public vehicle documents.
- Cancellation is allowed only while a booking is confirmed and has not started.
- Listings remain hidden until admin approval. A React/Vite admin screen now lists pending vehicles and calls the existing `reviewRentalVehicle` callable. Access requires a server-assigned `admin: true` custom claim; the callable independently enforces this claim.
- Rental payment is not included in this feature yet; the multi-currency/payment requirement must later extend payment support to rentals.

## Admin dashboard setup (FR-03)

From PowerShell:

~~~powershell
cd CSE412_Drive\apps\admin
npm install
Copy-Item .env.example .env.local
# Edit .env.local with your Firebase Web app values; never put service-account or Stripe secret keys here.
npm run dev
~~~

Open the local Vite URL printed in the terminal. Sign in with an administrator account that has the server-assigned `admin: true` custom claim. The page loads pending vehicle listings and uses `reviewRentalVehicle` to approve/reject them; browser clients cannot write approval fields directly. A configured Firebase project and an authorized admin account are required; no admin credentials are included in the repository.

Never disable Firestore rules to make the feature work.

## Tests and limits

The rental booking-window test checks rounding partial hours up, too-near start time, invalid end time, over-72-hour rentals and the 90-day advance limit. The existing backend integration scenario also covers owner approval, vehicle listing, rental booking, overlap rejection, cancellation and rebooking. The latest Firebase emulator integration run must pass before this requirement can be marked complete.

The Flutter CI workflow builds a **Firebase-emulator demo APK** when the build step succeeds. It is not a standalone production APK: it expects the Firebase emulators to run on the development computer. A configured Firebase release APK can be generated by CI only when the repository has the required Firebase secrets. Stripe test payment setup is separate.
