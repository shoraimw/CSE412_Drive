# DRIVE — Phase 3: Flutter, Authentication and Role-Based App

**CSE412 Software Engineering — East West University — Fall 2026**  
**Source of truth:** Phase 1 SRS, Phase 2 Cloud Functions and security rules, implementation brief.  
**Scope:** Functional Flutter account and role foundation. Ride-booking Maps, driver GPS/navigation, live trip tracking, payments and ML belong to subsequent phases.  
**Mobile platforms:** Android and iOS using one Flutter source tree. iOS builds require a Mac/Xcode.

## 1. Actual implementation delivered

- Flutter Material 3 mobile app with Riverpod dependency injection.
- Firebase Authentication: email/password registration, sign-in, email verification gate, reset-password email, Google native OAuth, international phone OTP.
- Server-side user profile through Phase 2 ensureProfile function; protected Firestore profile listener.
- Automatic signed-out/signed-in, verification, account-disabled, complete-profile and role-home navigation.
- Driver account application: vehicle type/model/plate, private licence/vehicle/photo upload, protected backend submission.
- Owner account application with business name, submitted to protected backend.
- Approved-driver home, online/offline Cloud Function switch, approved-owner home and own vehicle listing.
- English and Bangla localization with 115 translation keys, dark/light/system appearance.
- Form validation, accessible controls, loading/error states, widget/unit tests and GitHub Actions.

**Explicit scope boundary:** The rider landing page displays clearly identified upcoming features, not a fake booking workflow. Driver location updates and acceptance screens begin in Phase 5. The protected role tabs only appear after admin approval.

## 3. Windows: install and launch

Install the **latest stable Flutter SDK** and **Android Studio**, add the Flutter SDK bin directory to PATH, accept Android SDK licences, and create an Android Emulator. Keep **Git, Node.js 22 and Java 21** for the Firebase emulators. FlutterFire/Firebase production configuration is described later.

Run in PowerShell:

~~~powershell
flutter doctor -v

git clone https://github.com/shoraimw/CSE412_Drive.git
cd CSE412_Drive\apps\mobile

flutter create --project-name drive_mobile --org com.drive.cse412 --platforms=android,ios .
flutter pub get
flutter gen-l10n
flutter analyze
flutter test
~~~

**IMPORTANT:** Run flutter create without the --overwrite flag; this preserves the committed Dart source and widget tests while creating native Android Gradle and iOS Xcode projects.

**Android settings:** After generating, check android/app/build.gradle.kts (or build.gradle) and set minSdk to **24 or higher** for the current Firebase SDK major release if the generated setting is lower. Android needs INTERNET permission in the main manifest for real connectivity. The committed Android debug manifest enables cleartext localhost emulator connections in debug builds only; production release must not enable cleartext HTTP. Android Studio's emulator uses 10.0.2.2 to contact services on the computer hosting it.

## 4. Local Firebase Emulator setup

Keep all core backend services local while testing: Authentication 9099, Functions 5001 (asia-south1), Firestore 8080, Realtime Database 9000, Storage 9199 and Emulator UI 4000.

There are two supported modes:

- **Demo-only mode:** run without a config file. The app uses synthetic values and the `demo-drive-local` project. This is suitable for basic local testing; native Google sign-in needs real OAuth/Firebase configuration.
- **Google sign-in with local backend emulators:** keep the ignored file `apps/mobile/config/firebase.local.json` with the Firebase app configuration. The app uses its API key, app ID, sender ID and project ID while the core Firebase services are redirected to local emulators. The project ID must match between the app config and the emulator command.

### Terminal A — repository root

Set the Functions discovery timeout to **60000 milliseconds** (60 seconds), build the backend, and start emulators with the same project ID used by the app:

~~~powershell
$env:FUNCTIONS_DISCOVERY_TIMEOUT = "60000"
$cfg = Get-Content ".\\apps\\mobile\\config\\firebase.local.json" -Raw | ConvertFrom-Json
# One-time setup if the Firebase CLI says you are not authenticated:
npx.cmd firebase-tools login
npm.cmd --prefix services/functions run build
npx.cmd firebase-tools emulators:start --project $cfg.FIREBASE_PROJECT_ID --only auth,firestore,database,storage,functions
~~~

If using demo-only mode without `firebase.local.json`, use `--project demo-drive-local` instead. Do not start a second emulator session while the first is running. If startup reports ports already taken, stop the existing Firebase emulator process before retrying. Wait until the CLI says all emulators are ready and check that it does **not** report a failed Functions discovery before launching Flutter.

### Terminal B — `apps/mobile`

For Google sign-in with the local backend:

~~~powershell
flutter run --dart-define=DRIVE_EMULATOR=true --dart-define-from-file=config/firebase.local.json
~~~

For demo-only testing:

~~~powershell
flutter run --dart-define=DRIVE_EMULATOR=true
~~~

Keep `DRIVE_EMULATOR=true` enabled whenever using the local emulator setup. Never run the app against production services by mistake. The Android Emulator reaches the workstation at `10.0.2.2`; iOS Simulator uses `127.0.0.1`.

For a physical device on a trusted development LAN, use an accessible workstation address with explicit opt-in:

~~~powershell
flutter run --dart-define=DRIVE_EMULATOR=true --dart-define=DRIVE_EMULATOR_HOST=192.168.1.20
~~~

Replace the example local IP with the actual host and bind emulator services to the required interface using a secure development network. Do not expose Firebase emulators to the public internet. The Authentication Emulator UI is available at http://127.0.0.1:4000/auth.

## 5. Set up a real Firebase project (instead of emulator)

Firebase Console: https://console.firebase.google.com/

- Create a Firebase project and register Android/iOS apps using their generated native package/bundle IDs.
- Enable Email/Password, Google and Phone under Authentication sign-in providers.
- Create Firestore, Realtime Database and Storage; deploy Phase 2 security rules.
- Deploy the Phase 2 Cloud Functions to the **asia-south1** region. Cloud Functions production deployment needs Firebase Blaze billing.
- Register SHA-1/SHA-256 fingerprints for Android Google and Phone auth, add authorized domains for applicable provider flows, and configure native iOS URL schemes as required.
- Use Phone Authentication test numbers for development; real SMS may be rate-limited, billable or require a supported verification environment.
- Configure native Firebase apps with the FlutterFire CLI when necessary for OAuth integrations. This Flutter source uses explicit FirebaseOptions via dart-defines; generated firebase_options.dart is intentionally not imported.
- Admin custom claims are granted with the safeguarded Phase 2 grant-admin script; do not put administrator emails, JWTs or service-account keys in the mobile app.

On your computer only, create a private JSON file named **apps/mobile/config/firebase.local.json** with keys:

~~~json
{
  "FIREBASE_PROJECT_ID": "value from Firebase project settings",
  "FIREBASE_API_KEY": "value from registered Firebase app",
  "FIREBASE_APP_ID": "value from registered Android or iOS Firebase app",
  "FIREBASE_MESSAGING_SENDER_ID": "value from Firebase settings",
  "FIREBASE_STORAGE_BUCKET": "exact bucket from Firebase Storage",
  "FIREBASE_DATABASE_URL": "exact URL from Realtime Database",
  "GOOGLE_WEB_CLIENT_ID": "Web OAuth client ID configured in Google Cloud"
}
~~~

These are **illustrative labels, not working credentials**. All actual values must come from your newly registered Firebase project. The config file is Git-ignored; do not commit it, server secrets, or service-account private keys.

Launch with:

~~~powershell
cd CSE412_Drive\apps\mobile
flutter run --dart-define-from-file=config/firebase.local.json
~~~

For iOS use that platform's correct Firebase App ID in its own private config file. Do not pass DRIVE_EMULATOR=true against production.

| Key | Phase 3 purpose |
|---|---|
| FIREBASE_PROJECT_ID | Firebase project identity |
| FIREBASE_API_KEY | Firebase registered-client API key; not the Admin SDK secret |
| FIREBASE_APP_ID | Platform-specific Firebase application ID |
| FIREBASE_MESSAGING_SENDER_ID | Registered Firebase messaging sender identifier |
| FIREBASE_STORAGE_BUCKET | Driver document upload bucket |
| FIREBASE_DATABASE_URL | Later RTDB real-time updates; supply actual instance for future phases |
| GOOGLE_WEB_CLIENT_ID | Native GoogleSignIn server client configuration |
| GOOGLE MAPS / ROUTES keys | Not used in Phase 3; Phase 4 |
| Stripe/bKash/SSLCommerz secrets | Not used in Phase 3; Phase 6 and backend only |

## 6. Run and verify actual user stories

**US-01: Email/password account.** Create account with display name, email, 8+ character password. Firebase registers user and sends a verification email. Unverified email remains on verification screen until verification completes. Verified user completes a profile through ensureProfile; rider home opens.

**US-02: Google account.** After configuring native OAuth credentials, select Continue with Google. Native GoogleSignIn obtains an ID token; Firebase signs in with that credential. User profile is created in the same secure server flow.

**US-03: Phone OTP.** Select Continue with phone, enter international +880 format, wait for Firebase SMS verification/test code, enter six digits, then complete the user profile. App may require a real device, approved test phone, Play Services or reCAPTCHA depending on platform/provider rules.

**US-04: Lost password.** Enter registered email on login screen and tap Forgot password; Firebase issues its password-reset email (where permitted by the project configuration). No reset tokens are generated by the app.

**US-05: Driver approval.** Sign in and complete profile; Account > Become a driver. Select bike/car/premium, enter vehicle model/registration, choose distinct licence, vehicle document and photo. JPG/PNG/PDF files under 10 MB are uploaded privately to applications/UID in Storage. The backend checks paths and records pending. A privileged admin uses reviewDriverApplication; after approval the Driver tab appears. Refresh access before driver-claim-protected operations.

**US-06: Vehicle-owner approval.** Account > Become an owner, enter business name, submit. The backend marks the application pending. Once an admin approves, the Owner tab becomes visible. Owner dashboard reads only the user's own vehicle records.

**US-07: Appearance and language.** Account page selects English/Bangla and system/light/dark theme. Language choice is saved to the user profile via the backend; theme uses in-memory application state.

**US-08: Driver online toggle.** Approved drivers can toggle availability. The client calls setDriverAvailability, which re-checks admin approval on the server; Firestore updates the switch after completion. No GPS publishing occurs in this phase.

**Manual security test:** A signed-in non-admin must be denied when calling reviewDriverApplication or reviewOwnerApplication. A pending driver may not publish trusted location status as an approved driver, and the main rider UI must not provide an admin control.
